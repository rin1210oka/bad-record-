# Shuttle Note — Team Edition

1チームのメンバーと試合を共同管理するバドミントン記録アプリ。React / TypeScript / Vinext と Cloudflare D1を使用します。

## 仕様

- メンバー登録、名前・所属・在籍／休止の編集
- 編集時は登録済みの情報を初期表示し、学年・基準年度も入力済みで確認できる。生年月日は変更時の再計算用として使用
- 誤登録した選手の削除と「削除済みの選手」からの復元。過去の試合・名前・選手IDを保持し、新規入力候補からは除外
- 登録名は全角カタカナ・空白なしに自動統一（ひらがな・半角カナに対応）。漢字の読みは入力者が指定
- 選手名をタップして所属・状態・区分別成績・選手視点の試合履歴を表示
- 「この部に所属している／していた」の回答から内部・外部を決め、生年月日から年度ごとの学年・一般・OB/OG表示を計算
- 高校入学の基準年度から日本時間の4月1日ごとに表示学年を計算。生年月日はブラウザー内の計算専用で保存・送信しない
- 所属経験ありは内部で卒業相当年度からOB・OG、なしは外部で卒業相当年度から一般。所属と在籍歴の二重入力をなくす
- 内部の選手は「何期生」を数字で登録できる。期生は生年月日から推測せず、登録した番号を卒業後も保持する
- 一覧の区分は「現役・○期生」「OB/OG・○期生」「外部・高○」「外部・一般」。既存選手など期生が不明な場合は「期生未設定」と表示
- 生年月日が不明な場合の基準年度入力と学年補正に対応。学年補正は指定年度から翌年度以降に引き継ぎ、入力可否は別に設定
- 選手一覧を年度・所属・学年で絞り込み、選択年度の出場成績を確認
- 選手は内部の現役→OB・OG→外部の順。現役・外部の高校生は高3→高2→高1、OB・OGは期生番号の小さい順にし、同じ学年・期生の中は50音順。未設定項目は各区分の末尾に表示
- 試合入力の検索候補も同じ順で表示。引退時期では学年・区分を変えず、年度に合わせて進級・卒業表示を更新
- 大会親データを作らない、1試合単位の直接入力
- 区分：公式戦／練習試合／ゲーム練
- シングルス／ダブルス。セット数・終了点数を固定せず、入力時にセットを追加・削除
- 試合カードと選手の試合履歴はダブルスの選手名を1人1行で表示。保存済みのペアの順序と得点の対応は保持
- 得点の多い側がセット勝者。獲得セット数が多い側が試合勝者、同数なら引き分け。同点セットは双方の獲得数に加算しない
- 成績は勝ち・負け・引き分けを分けて表示。勝率は引き分けを除いて計算
- 対外対戦の相手名入力、部内対戦の登録メンバー選択
- 試合入力の登録選手は名前・所属の検索候補から選択。ひらがな・半角カナ・空白に対応し、選択済みの選手の重複を防ぐ
- 部内戦は1件から両側の選手の出場・勝敗に反映。チーム対外勝率からは除外
- 検索、区分・選手の絞り込み、CSV出力
- 記録の編集・論理削除、30秒ごとと画面復帰時の再取得
- 同時編集は版番号で衝突を検出。同条件の試合は重複を警告し、別試合なら明示確認後に保存

## 保存とアクセス

記録はブラウザーではなくD1に保存します。個人ログイン後、名簿と試合はチームで共有して閲覧・更新します。入力者を記録します。各試合の「自分の振り返り」は個人アカウントIDを所有者として保存し、本人だけが閲覧・編集できます。管理担当にも振り返りの閲覧権限を与えません。共有のAPI・メモ・検索・CSVには個人の振り返りを含めません。

部員の入場は部の合言葉・ログイン名・数字6桁の暗証番号を使います。初回は管理担当が発行する選手ごとの招待コードで、登録済みの選手と個人アカウントをひも付けます。メールアドレスは不要です。初期設定だけは所有者のSites認証を確認し、`ACCESS_SETUP_OWNER_EMAIL`と一致する所有者が最初の管理担当と合言葉を設定します。未設定・未ログインの状態では名簿や試合を返しません。

暗証番号は平文では保存せず、個別のソルト・サーバー専用の`ACCESS_PEPPER`を用いたPBKDF2で保管します。6桁を採用するため、試行回数をアカウント単位で制限し、5回続けて失敗した場合は個別の復旧コードで再設定します。招待コードと復旧コードは十分に長い乱数で、使うと無効になります。管理担当による暗証番号の代理設定や選手ひも付けの変更は用意せず、別人に振り返りが引き継がれないようにします。

セッションは30日で期限切れとなり、HttpOnly・SameSite=Strict（HTTPSではSecure）のCookieで保持します。停止・暗証番号変更・復旧・権限変更時はセッションを失効させます。公開範囲を変更する前に、全データAPIが個人ログインを検証することを確認します。Sitesのプラットフォーム認証の実装は初期設定用として残します。

運用上の「本人だけ」はアプリの権限で制御します。保存内容のエンドツーエンド暗号化ではなく、インフラやDBの運用権限からも読めないという意味ではありません。

旧個人版のlocalStorageデータはクラウドへ自動移行しません。サンプルやテスト用記録を本番DBに投入しません。

既存の登録名は一括変更しません。編集して保存するときにカタカナへ統一します。選手IDは変わらないため、過去の試合との関連は保持されます。

所属・学年が不明な既存選手は未設定として移行します。新規試合には試合日の学年と入力時点の所属設定をサーバー側で保存します。プロフィールや年度が変わっても保存済みの表示は保持します。既存試合のメモ編集では不明な過去属性を埋めず、未記録として表示します。試合日や出場者を変更した場合は、その変更に合わせて属性を記録します。所属の完全な年表は管理しません。

既存の所属と在籍歴は一括変換しません。両者が新しい回答と一致しない選手も、編集時に「現在の登録を維持」で元の情報を保持できます。所属経験の回答を明示変更するときは`hasTeamHistory`を送信し、サーバーが所属と在籍歴を一緒に設定します。保存済みの基準年度があれば生年月日の再入力は不要です。旧形式のAPI編集は互換性を維持します。

所属先・備考は詳細・編集画面で確認し、メンバー一覧では区分・期生を表示します。

期生番号は任意の整数（1〜9999）として保存し、未入力は未設定です。外部の表示には使用しません。既存クライアントが期生番号を送らない編集でも、登録済み番号を保持します。過去の試合に保存済みの所属・学年は変更しません。

## 開発

依存導入後 `npm run dev`。`.dev.vars`にローカル専用の`ACCESS_PEPPER`（32文字以上の十分に長い乱数）と`ACCESS_SETUP_OWNER_EMAIL=seedy@sites.test`を設定します。ループバックで `/signin-with-chatgpt?return_to=/` を開くと初期設定用の開発認証が使えます。D1のローカルと本番は別です。本番の同名設定はSitesのランタイムシークレットに設定し、ソースや公開ファイルには含めません。運用後の`ACCESS_PEPPER`の安易な変更は既存の認証情報を無効にするため避けます。

スキーマ変更時は `npm run db:generate`。`drizzle/` の生成SQLとメタデータをコミットします。ローカルへの適用とSites公開はスターターの手順に従います。

`node --test tests/*.test.mjs` で得点・同時編集・重複・認証・本人限定の振り返りをテストします。`node node_modules/typescript/bin/tsc --noEmit` で型を確認します。

`app/team-app.tsx` が画面、`lib/team-domain.ts` が入力検証、`lib/team-store.ts` が共有DBの操作、`app/api/` がAPIです。Cの構造体はTypeScriptの型、`matches[]` はAPIから受け取る試合配列に対応します。
